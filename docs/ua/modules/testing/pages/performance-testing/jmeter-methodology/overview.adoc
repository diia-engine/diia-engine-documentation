Цей розділ описує комплексну методологію навантажувального тестування реєстрів на Платформі Diia.Engine на базі Apache JMeter. Методологія охоплює як інфраструктурну частину (генерація навантаження), так і прикладну (тестовий регламент із набором специфічних бізнес-процесів).

[#methodology-goal]
== Мета методології

Головна мета — забезпечити стандартизований, масштабований та відтворюваний підхід до тестування продуктивності реєстрів під екстремальними навантаженнями.

Замість базової генерації HTTP-запитів, методологія передбачає симуляцію реальної поведінки системи: реєстрацію користувачів, роботу зі складними транзакціями в базі даних, асинхронне оновлення масових сутностей та завантаження/вивантаження файлів.

[#high-level-achitecture]
== Високорівнева архітектура

Інфраструктура навантажувального тестування побудована за принципом ізольованих компонентів та динамічного масштабування. Основні вузли:

* **Jenkins (CI/CD Orchestrator):** Керує життєвим циклом тестів, ініціалізує середовища та запускає Job DSL скрипти (`seedjob.groovy`).
* **JMeter Agents (Master-Slave модель):** Динамічні Docker-контейнери, які генерують безпосереднє навантаження.
* **Моніторинг (Grafana + InfluxDB):** Збір метрик у режимі реального часу для аналізу деградації продуктивності та пошуку вузьких місць.
* **Traefik:** Зворотний проксі для управління трафіком до тестових компонентів.

[#jmeter-scaling-strategy]
== Стратегія масштабування JMeter

Для генерації надвеликого навантаження запуск одного контейнера з JMeter є технічно неможливим. Запропонована методологія суворо вимагає розподілу навантаження на декілька контейнерів (агентів) з наступних причин:

1. **Вичерпання пам'яті (OutOfMemoryError):** Кожен потік JMeter вимагає виділення RAM. Крім того, при тестуванні завантаження/вивантаження файлів JMeter намагається кешувати дані в пам'яті. Розподіл на агентів ізолює споживання пам'яті.
2. **Перемикання контексту CPU (Context Switching):** При тисячах потоків в одному процесі процесор витрачає більше часу на перемикання між потоками, ніж на генерацію HTTP-запитів.
3. **Ліміти файлових дескрипторів (ulimit):** Кожне HTTP-з'єднання відкриває сокет. Розподіл на контейнери дозволяє обійти жорсткі ліміти ОС Linux на кількість відкритих файлів для одного процесу.
4. **Стійкість до збоїв (Resilience):** Якщо через аномальну відповідь API один контейнер впаде з помилкою пам'яті, інші агенти продовжать генерувати навантаження, і тест не буде повністю провалено.

[#business-processes]
== Структура тестового регламенту (Бізнес-процеси)

Для покриття ключових аспектів роботи реєстрів розроблено окремий тестовий проєкт (регламент), який містить 6 основних сценаріїв:

1. `feature-unregistered-role` — Тест процесу реєстрації користувача з перевизначенням ролі користувача.
2. `feature-nested-entity-test-process` — Тестування збереження складних сутностей (Nested Entity) в рамках однієї транзакції.
3. `reference-iban-update-process` — Асинхронне оновлення масових сутностей (на прикладі оновлення IBAN).
4. `feature-test-read-all-grid` — Перегляд великих масивів даних. Генерація гріда ізольована в коді (без БД) для фокусування навантаження на сервіс `form-submission-validation`.
5. `feature-multiple-file-saving` — Завантаження масивів файлів (`multipart/form-data`) з оптимізацією використання RAM агента.
6. `feature-zvit-pdf-bp` — Запит на формування та скачування багатосторінкових згенерованих витягів.

[#code-organization-dry]
== Організація коду та DRY

Важливою частиною методології є оптимізація скриптів:

* **Gradle:** Спільні таски та налаштування винесені в окремі файли (наприклад, `gradle/scenarios/common.gradle`), що запобігає дублюванню коду між сценаріями.
* **Передача параметрів:** Використовується суворий контроль типів при передачі змінних (Properties vs Environment Variables) для уникнення проблем з парсингом масивів аргументів у Groovy.
