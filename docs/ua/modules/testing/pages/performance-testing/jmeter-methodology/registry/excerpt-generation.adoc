= Процес роботи з файлами (генерація складних витягів)
include::platform:ROOT:partial$templates/document-attributes/default-set-ua.adoc[]

Цей розділ описує налаштування регламенту реєстра для проведення навантажувального тестування процесу формування, генерації та скачування важких багатосторінкових PDF-витягів на основі даних із реєстру.

[#liquibase]
== Вимоги до моделі даних (Liquibase)

Для забезпечення логіки генерації звітів регламент повинен містити довідник факторів, умови пошуку для них та процедуру початкового наповнення системи.

[#create-table]
=== Створення таблиці довідника

Довідникова таблиця `factor` зберігає перелік бізнес-факторів, які зчитуються процесом під час формування витягу.

.Таблиця `factor` (data-model/factor/tables.xml)
[source,xml]
----
<changeSet id="table factor" author="registry_owner">
    <createTable tableName="factor" ext:historyFlag="true" remarks="Довідник всіх факторів">
        <column name="factor_id" type="UUID" defaultValueComputed="uuid_generate_v4()" remarks="Ідентифікатор фактору">
            <constraints nullable="false" primaryKey="true" primaryKeyName="pk_factor_id"/>
        </column>
        <column name="name" type="TEXT" remarks="Назва фактору">
            <constraints nullable="false"/>
        </column>
    </createTable>
</changeSet>
----

[#create-sc]
=== Умови пошуку (Search Conditions)

Для вичитування повної інформації про фактори у регламенті створюється умова пошуку `factor_all` із сортуванням за назвою.

.Пошуковий критерій `factor_all` (data-model/factor/searchConditions.xml)
[source,xml]
----
<changeSet author="registry owner" id="create SC factor_all">
    <ext:createSearchCondition name="factor_all">
        <ext:table name="factor" alias="f">
            <ext:column name="factor_id"/>
            <ext:column name="name" sorting="asc"/>
        </ext:table>
    </ext:createSearchCondition>
</changeSet>
----

[#prepopulation]
=== Передзаповнення даних (Prepopulation)

Наповнення довідника факторів виконується через виклик вбудованої процедури `p_load_table_from_csv`, яка завантажує записи із зовнішнього файлу.

.Препопуляція таблиці `factor` (data-model/factor/populate.xml)
[source,xml]
----
<changeSet author="registry owner" id="load data to dictionaries">
    <sql dbms="postgresql" endDelimiter=";" splitStatements="true" stripComments="true">
       CALL p_load_table_from_csv('factor','${dataLoadPath}feature/Factors_test.csv', array['name']);
    </sql>
</changeSet>
----

[NOTE]
====
Використовуйте готовий довідниковий файл _link:{attachmentsdir}/jmeter-methodology/data/Factors_test.csv[Factors_test.csv]_, який містить **36 еталонних рядків** факторів для забезпечення коректної ініціалізації бази даних під час розгортання тестового регламенту.
====

[#ui-forms]

Сценарій передбачає перегляд завантажених даних чиновником через інтерфейс користувача, для чого у регламенті розробляється **одна форма**:

* `feature-read-factor-data-zvit` — форма для відображення та перевірки переліку факторів із бази даних перед стартом генерації.

[TIP]

Використовуйте файл _link:{attachmentsdir}/jmeter-methodology/forms/feature-read-factor-data-zvit.json[feature-read-factor-data-zvit.json]_ із готовою структурю форми для економії часу.

[#integration-prerequisites]
== Інтеграційні передумови та пайплайн

Процес ініціюється чиновником (Officer), тому перед запуском основного навантаження пайплайн виконує стандартні кроки підготовки середовища:

1. **Генерація користувачів (Gradle):** Створення необхідної кількості унікальних чиновників (officers).
> !!! 🔗 <<лінк на сторінку: генерація тестових даних та робота з Gradle>>

2. **Оновлення мок-сервісу:** Патчинг `ConfigMap` мок-сервісу для стабільної емуляції суміжних систем.
> !!! 🔗 <<лінк на сторінку: оновлення ConfigMap для мок-сервісів>>

3. **Очищення середовища Keycloak (JMeter):** Видалення попередніх тестових записів користувачів.
> !!! 🔗 <<лінк на сторінку: jmx скрипт видалення користувачів>>

4. **Створення користувачів у Keycloak (JMeter):** Масове завантаження нових чиновників у Keycloak.
> !!! 🔗 <<лінк на сторінку: jmx скрипт створення користувачів>>

5. **Запуск головного тесту:** Виконання JMX-сценарію, який ініціює запити на формування PDF-витягів, циклічно перевіряє статус їх готовності та скачує фінальний файл.
> !!! 🔗 <<лінк на сторінку: моделювання та запуск головного jmx тесту>>

[WARNING]
====
Оскільки цей тест передбачає скачування великих бінарних файлів (PDF) у багатопотоковому режимі, у налаштуваннях `HTTP Request` головного тесту необхідно активувати оптимізацію роботи з RAM, щоб уникнути падіння JMeter-агентів із помилкою `OutOfMemoryError`.
====

[#bp-config-and-rbac-setup]
== Конфігурація бізнес-процесів та RBAC доступ

Регламент містить головний бізнес-процес для створення запиту на витяг та окремий підпроцес, який відповідає за циклічну перевірку статусу генерації файлу.

[cols="1,1", options="header"]
|===
| Параметр | Опис
| Process Definition ID | `feature-zvit-pdf-bp`
| Process Definition Name | `Процес для генерування pdf звітів`
2+| RBAC
| bp-auth/officer.yml | `op-regression`
|===

[#rbac-setup]
=== Налаштування RBAC

Конфігурація прав доступу для ролі `op-regression` прописується у файлі `bp-auth/officer.yml`:

[source,yaml]
----
authorization:
  realm: 'officer'
  process_definitions:
    - process_definition_id: "feature-zvit-pdf-bp"
      process_name: "Процес для генерування pdf звітів"
      process_description: "Процес для генерування pdf звітів"
      roles:
        - 'op-regression'
----
