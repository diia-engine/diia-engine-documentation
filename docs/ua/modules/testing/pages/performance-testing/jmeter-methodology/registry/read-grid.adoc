Цей розділ описує налаштування регламенту реєстра для проведення навантажувального тестування процесу перегляду та обробки великої кількості записів через компонент інтерфейсу Edit Grid.

[#bp-design]
== Бізнес-процес

Для цього сценарію передбачено **простий бізнес-процес**, який складається лише з однієї користувацької задачі (User Task). Мета цього кроку — відрендерити форму з таблицею та прийняти масивний пейлоад (payload).

[#ui-forms]
== Форми (UI Forms)

Регламент використовує одну форму для відображення таблиці (гріда) з даними.

* `feature-first-grid`

[TIP]
====
Використовуйте файл _link:{attachmentsdir}/jmeter-methodology/forms/feature-first-grid.json[feature-first-grid.json]_ із готовою формою для цього бізнес-процесу, щоб не створювати її з нуля.
====

[#data-generation]
== Особливості генерації даних (Payload)

[NOTE]
====
На відміну від інших сценаріїв, де використовується препопуляція бази даних через Liquibase, у цьому кейсі **генерація записів буде відбуватися безпосередньо в JMeter (`.jmx` скрипті)**.
====

Згенерований масив даних передаватиметься єдиним великим пейлоадом. Це дозволяє **імітувати ручне заповнення великої кількості рядків** у компоненті Edit Grid реальним користувачем та створює цільове навантаження на сервіс `form-submission-validation`.

xref:testing:performance-testing/jmeter-methodology/pipelines.adoc#pipeline-data-generation[Генерація тестових даних через Gradle та Groovy]

[#integration-prerequisites]
== Інтеграційні передумови та пайплайн

Тестування ініціюється від імені чиновника (Officer). Пайплайн підготовки до запуску основного тесту є стандартизованим і складається з наступних кроків:

1. **Генерація користувачів (Gradle):** Створення пулу унікальних тестових чиновників (officers).
xref:testing:performance-testing/jmeter-methodology/pipelines.adoc#pipeline-data-generation[Генерація тестових даних через Gradle та Groovy]

2. **Оновлення мок-сервісу:** Патчинг `ConfigMap` мок-сервісу згенерованими даними для забезпечення стабільної інтеграції.
xref:testing:performance-testing/jmeter-methodology/pipelines.adoc#pipeline-patch-configmap[Patch ConfigMap у тестовому середовищі]

3. **Очищення середовища Keycloak (JMeter):** Видалення існуючих тестових користувачів у Keycloak для уникнення дублікатів.
xref:testing:performance-testing/jmeter-methodology/pipelines.adoc#jmxdeletekeyclokofficers-task[jmxDeleteKeycloakOfficers]

4. **Створення користувачів у Keycloak (JMeter):** Масове створення підготовлених чиновників у Keycloak.
xref:testing:performance-testing/jmeter-methodology/pipelines.adoc#jmxdeletekeyclokofficers-task[jmxCreateKeycloakOfficers]

5. **Запуск головного тесту:** Виконання JMX-сценарію, який надсилає масивні пейлоади в ініційований бізнес-процес.
xref:testing:performance-testing/jmeter-methodology/pipelines.adoc#pipeline-jmeter-run[Запуск основного JMeter Test Plan]

[#rbac-setup]
=== Налаштування RBAC

Правила авторизації для чиновників повинні бути задекларовані у файлі `bp-auth/officer.yml` наступним чином:

[source,yaml]
----
authorization:
  realm: 'officer'
  process_definitions:
    - process_definition_id: "feature-test-read-all-grid"
      process_name: "Процес для перегляду великої кількості записів"
      process_description: "Процес для перегляду великої кількості записів"
      roles:
        - 'op-regression'
----

[TIP]
====
Використовуйте файл _link:{attachmentsdir}/jmeter-methodology/feature-test-read-all-grid.bpmn[feature-test-read-all-grid.bpmn]_ із готовою схемою бізнес-процесу для прикладу.
====
