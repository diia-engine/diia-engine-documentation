= Jenkins Pipelines та Оркестрація Навантажувальних Тестів
include::platform:ROOT:partial$templates/document-attributes/default-set-ua.adoc[]

:sectlinks:

Цей документ детально описує принципи побудови, структуру та життєвий цикл Jenkins-пайплайнів, що використовуються для автоматизації навантажувального тестування. Особлива увага приділяється інтеграції з Gradle для оркестрації тестових сценаріїв та генерації даних.

[#general-principles]
== Загальні принципи та підходи до створення пайплайнів

Автоматизація навантажувального тестування в проєкті базується на наступних ключових принципах:

*   **Configuration as Code (CaC):** Усі конфігурації Jenkins-джоб, включаючи їхні параметри та логіку виконання, зберігаються у системі контролю версій (Git) у вигляді Groovy-скриптів (Job DSL). Це забезпечує версіонування, прозорість та легкість відтворення середовища CI/CD.
*   **Single Source of Truth (Git):** Git-репозиторій є єдиним джерелом істини для всіх тестових сценаріїв та їхніх конфігурацій. Будь-які зміни, додавання або видалення тестів відбуваються шляхом модифікації файлів у репозиторії, а не через ручні операції в Jenkins UI.
*   **Модульна структура:** Проєкт має чітко визначену модульну структуру, де кожен компонент (пайплайни, скрипти навантаження, генератори даних) ізольований у відповідній директорії. Це сприяє легкості підтримки, розширюваності та повторному використанню коду.
*   **Динамічна генерація джоб:** Замість ручного створення Jenkins-джоб, використовується механізм Seed Job, який автоматично сканує репозиторій та генерує/оновлює тестові пайплайни на основі декларативних конфігурацій.

[#ci-directory-structure]
== Структура директорії `ci/`

Директорія `ci/` є центральним сховищем для всіх компонентів, що стосуються CI/CD процесів у Jenkins. Вона організована таким чином, щоб забезпечити ефективне керування пайплайнами та їхню ізоляцію.

[source,text]
----
ci
├── idea.gdsl
├── pipeline.gdsl
├── pipelines/
│   ├── feature-multiple-file-saving/
│   │   ├── params.json
│   │   └── pipeline.groovy
│   ├── feature-nested-entity-test-process/
│   │   ├── params.json
│   │   └── pipeline.groovy
│   ├── ... (інші сценарії)
│   └── reference-iban-update-process/
│       ├── params.json
│       └── pipeline.groovy
├── PatchMockService.groovy
└── seedjob.groovy
----

[#seedjob-groovy]
=== `seedjob.groovy` (Jenkins Job DSL Seed Job)

Цей Groovy-скрипт є базовою джобою (Seed Job), яка відповідає за динамічну генерацію та оновлення всіх Jenkins Pipeline джоб для навантажувального тестування.

**Призначення:** Автоматизує створення, оновлення та видалення Jenkins-джоб на основі файлів, що зберігаються у системі контролю версій (Git).

**Механізм роботи:**

*   Скрипт сканує директорію `ci/pipelines/`.
*   Для кожної піддиректорії, що містить `pipeline.groovy` та/або `params.json`, він створює або оновлює відповідну Jenkins Pipeline джобу.
*   Назва джоби формується за шаблоном `perf-test-<назва-сценарію>`.
*   Файл `params.json` використовується для автоматичного створення параметрів збірки (`Build with Parameters`) в Jenkins UI, що дозволяє користувачам легко налаштовувати запуск тестів.

**Тригери:** Seed Job налаштована на опитування репозиторію (SCM Polling) з певною періодичністю (наприклад, кожні 15 хвилин). Запуск генерації відбувається лише у випадку виявлення нових коммітів у цільовій гілці.

**Керування життєвим циклом:** Завдяки директиві `removedJobAction('DELETE')`, Seed Job автоматично видаляє Jenkins-джоби, якщо відповідні файли сценаріїв були видалені з Git-репозиторію.

[NOTE]
====
Використання `seedjob.groovy` усуває необхідність ручного створення джоб через інтерфейс Jenkins. Усі зміни у пайплайнах або додавання нових тестів застосовуються автоматично після запуску Seed-джоби `*seed-job-pipeline-generator*`.
====

[#gdsl-files]
=== `idea.gdsl` та `pipeline.gdsl` (Groovy DSL Support)

Ці файли призначені для покращення досвіду розробника (Developer Experience) при написанні Jenkins Pipeline скриптів у IDE (наприклад, IntelliJ IDEA).

*   **Призначення:** Надають статичний аналіз коду, автодоповнення (autocomplete), підсвічування синтаксису та валідацію для Jenkins Pipeline DSL.
*   **Механізм роботи:** IDE використовує ці файли для розуміння структури та доступних функцій Jenkins Pipeline, що допомагає уникнути синтаксичних помилок та прискорює розробку.
*   **Важливо:** Ці файли ігноруються агентами Jenkins під час виконання збірки. Вони не впливають на логіку виконання пайплайнів, а слугують виключно для підтримки розробки.

[#pipelines-directory-description]
=== Директорія `pipelines/`

Ця директорія містить піддиректорії для кожного окремого тестового сценарію. Кожен сценарій є ізольованим і має власну конфігурацію.

**Структура сценарію:** Кожна піддиректорія сценарію (наприклад, `feature-multiple-file-saving/`) містить два обов'язкові файли:

*   `params.json`: JSON-файл, що описує вхідні параметри для пайплайну. `seedjob.groovy` парсить цей файл для створення параметризованого інтерфейсу (`Build with Parameters`) в Jenkins. Типові параметри включають `KUBE_URL`, `NAMESPACE`, `MOCK_SERVICE_ROUTE_URL`, `THREADS` тощо.
*   `pipeline.groovy`: Jenkinsfile, що визначає послідовність кроків виконання тесту. Він включає checkout коду, підготовку оточення, генерацію тестових даних, виклик Gradle-тасок, агрегацію логів та публікацію звітів.

[#patchmockservice-groovy-description]
=== `PatchMockService.groovy` (Утилітарний скрипт)

Цей Groovy-скрипт є утилітарним класом, призначеним для взаємодії з Kubernetes API безпосередньо з Jenkins Pipeline.

**Призначення:** Динамічне оновлення конфігурацій (наприклад, `ConfigMap`) мок-сервісу перед початком генерації навантаження.

**Використання:** Пайплайни викликають цей скрипт для внесення змін до тестового оточення, що дозволяє адаптувати мок-сервіс під конкретні потреби тестового сценарію (наприклад, завантаження згенерованих тестових даних).

[#gradle-orchestration]
== Gradle таски для оркестрації тестів

Gradle відіграє ключову роль в оркестрації всіх етапів навантажувального тестування, від підготовки даних до запуску JMeter-сценаріїв та обробки результатів. Конфігурація Gradle побудована на принципах DRY (Don't Repeat Yourself) та динамічної генерації завдань.

[#build-gradle-overview]
=== `build.gradle` (Основний файл конфігурації)

Файл `build.gradle` є головним конфігураційним файлом проєкту. Він виконує наступні функції:

*   **Керування залежностями:** Визначає бібліотеки, необхідні для роботи генераторів даних (`datafaker`, `commons-compress`) та для локальної валідації Jenkins Job DSL скриптів (`jenkins-core`, `job-dsl-core`).
*   **Передача властивостей:** Блок `tasks.withType(JavaExec).configureEach { systemProperties project.properties }` гарантує, що всі змінні, визначені у `gradle.properties` або передані через командний рядок (`-P`), будуть доступні всередині Groovy-скриптів генераторів.
*   **Динамічна ініціалізація сценаріїв:** Замість ручного визначення таск для кожного JMeter-сценарію, `build.gradle` використовує ітерацію по масиву конфігурацій. Для кожного сценарію викликається замикання `registerJmeterTask` (визначене у `common.gradle`), яке динамічно створює Gradle-таску для запуску JMeter. Це дозволяє легко додавати нові сценарії без зміни основної логіки `build.gradle`.

[source,groovy]
----
// Фрагмент build.gradle: Динамічна ініціалізація сценаріїв
[
        [
                name: 'feature-nested-entity-test-process'
        ],
        // ... інші сценарії
].each { scenario ->
    def scenarioName = scenario.name
    def specificParams = scenario.extraArgs ?: []
    // ... формування параметрів
    def taskName = "run${camelCaseName}"

    registerJmeterTask(taskName, scenarioName, finalParams)
}
----

[#common-gradle-overview]
=== `gradle/scenarios/common.gradle` (Спільні конфігурації)

Файл `common.gradle` містить всю повторювану логіку, пов'язану з виконанням JMeter та допоміжними операціями. Він імпортується в `build.gradle` через `apply from: "gradle/scenarios/common.gradle"`.

Тут зосереджено два основні типи завдань:

*   **Службові таски (Service Tasks):** Завдання для підготовки оточення, керування тестовими даними та користувачами.
*   **Замикання `registerJmeterTask`:** Ядро оркестрації, яке динамічно реєструє таски для запуску JMeter.

[#detailed-gradle-tasks]
==== Детальний опис ключових Gradle таск

Нижче наведено опис важливих Gradle-таск, які використовуються в пайплайнах:

[#jmxcleanup-task]
*   `*jmxCleanup*` (тип `Delete`)
**   **Призначення:** Видалення тимчасових файлів та звітів перед новим запуском тесту.
**   **Дія:** Зчитує змінну середовища `SCENARIO_NAME` та видаляє директорії `out/` та `out/html` для конкретного сценарію. Це забезпечує чисте середовище для кожного запуску.
**   **Використання:** `gradle jmxCleanup`

[#jmxdeletekeyclokofficers-task]
*   `*jmxDeleteKeycloakOfficers*` / `*jmxCreateKeycloakOfficers*` (тип `Exec`)
**   **Призначення:** Керування тестовими користувачами в Keycloak.
**   **Дія:** Запускають відповідні службові JMeter-сценарії (`delete-keycloak-users.jmx` та `create-keycloak-users.jmx`) у non-GUI режимі. Ці сценарії відповідають за видалення або створення тестових облікових записів у Keycloak, що є частиною підготовки або очищення тестового оточення.
**   **Використання:** `gradle jmxDeleteKeycloakOfficers`, `gradle jmxCreateKeycloakOfficers`

[#groovygenerateofficermockusers-task]
*   `*groovyGenerateOfficerMockUsers*`, `*groovyGenerateCitizenMockUsers*` (тип `JavaExec`)
**   **Призначення:** Генерація тестових даних для користувачів.
**   **Дія:** Запускають Groovy-класи генераторів (`MockUsersOfficerGenerator`, `MockUsersCitizenGenerator`), які створюють реалістичні дані (ПІБ, РНОКПП, ЄДРПОУ) та зберігають їх у CSV-файли. Ці файли потім можуть бути використані для синхронізації з Keycloak або мок-сервісами.
**   **Використання:** `gradle groovyGenerateOfficerMockUsers`, `gradle groovyGenerateCitizenMockUsers`

[#groovygenerateexecutionplan-task]
*   `*groovyGenerateExecutionPlan*` (тип `JavaExec`)
**   **Призначення:** Генерація плану виконання для складних бізнес-сутностей.
**   **Дія:** Запускає Groovy-клас `NestedEntityDataGenerator`, який формує `execution-plan.csv` з атрибутами транзакцій (тип наказу, номер, дата).
**   **Використання:** `gradle groovyGenerateExecutionPlan`

[#registerjmetertask-closure]
*   `*registerJmeterTask*` (замикання)
**   **Призначення:** Динамічна реєстрація Gradle-таск для запуску JMeter-сценаріїв.
**   **Дія:** Це замикання приймає назву таски, ім'я сценарію та додаткові аргументи. Воно автоматично:
***   Створює необхідні директорії для вихідних файлів (`out/`, `out/html`).
***   Формує повний масив аргументів для CLI-виклику JMeter у non-GUI режимі (`-n`).
***   Передає параметри профілю навантаження (`-JTHREADS`, `-JRAMP_UP`) з Gradle-властивостей.
***   Прив'язує шляхи до звітів (`-l results.csv`, `-e -o htmlDir`) та передає `BUILD_ID` з Jenkins для унікальної ідентифікації запуску.
**   **Приклад використання (в `build.gradle`):**
        ```groovy
        registerJmeterTask('runFeatureNestedEntityTestProcess', 'feature-nested-entity-test-process')
        ```
*   **Динамічно згенеровані таски:** Для кожного сценарію, визначеного в `build.gradle`, створюється таска за шаблоном `run<CamelCaseScenarioName>` (наприклад, `runFeatureNestedEntityTestProcess`). Ці таски є основними для запуску JMeter-сценаріїв.
**   **Використання:** `gradle runFeatureNestedEntityTestProcess -PTHREADS=100 -PRAMP_UP=10`

[NOTE]
====
Параметри типу `THREADS` та `RAMP_UP` зчитуються через `project.findProperty()`, що означає, що вони передаються в Gradle через прапорець `-P` (наприклад, `./gradlew runFeature... -PTHREADS=100 -PRAMP_UP=10`). Натомість `BUILD_NUMBER` зчитується через `System.getenv()`, оскільки це нативна змінна середовища, яку інжектує Jenkins під час запуску Pipeline.
====

[#pipeline-execution-lifecycle]
== Життєвий цикл виконання пайплайну

Цей розділ описує наскрізний процес автоматизації навантажувального тестування, від ініціалізації джоб у Jenkins до збору метрик та очищення середовища.

[#pipeline-init-generation]
*   **Ініціалізація та генерація джоб (Jenkins Seed Job)**
**   Процес починається з `seed-job-pipeline-generator`, яка використовує `ci/seedjob.groovy` для сканування директорії `ci/pipelines/`.
**   На основі знайдених `pipeline.groovy` та `params.json` файлів, Seed Job динамічно створює або оновлює Jenkins Pipeline джоби (наприклад, `perf-test-feature-nested-entity`).

[#pipeline-user-launch]
*   **Запуск пайплайну користувачем**
**   Користувач (тестувальник або інший CI/CD пайплайн) ініціює запуск конкретної тестової джоби через Jenkins UI, використовуючи інтерфейс *Build with Parameters*.
**   На цьому етапі задаються ключові параметри тесту (наприклад, кількість потоків, тривалість, URL мок-сервісу), які передаються як змінні середовища.

[#pipeline-checkout]
*   **Отримання вихідного коду (Checkout)**
**   Jenkins-агент виділяє ізольований робочий простір (Workspace) та виконує `git checkout`, завантажуючи актуальну версію репозиторію з усіма конфігураціями, скриптами та JMeter-сценаріями.

[#pipeline-local-cleanup]
*   **Локальне очищення**
**   Пайплайн викликає Gradle-таску `jmxCleanup`. Ця таска видаляє всі попередні результати тестів, логи та тимчасові файли, забезпечуючи чисте середовище для поточного запуску.

[#pipeline-data-generation]
*   **Генерація тестових даних через Gradle та Groovy**
**   Викликаються відповідні Gradle-таски (наприклад, `groovyGenerateOfficerMockUsers`, `groovyGenerateExecutionPlan`).
**   Ці таски запускають Groovy-класи генераторів, які використовують бібліотеку `net.datafaker:datafaker` для створення реалістичних українських персональних даних або специфічних атрибутів транзакцій.
**   Згенеровані дані зберігаються у вигляді CSV-файлів у директорії `jmeter/test-data/`.

[#pipeline-patch-configmap]
*   **Patch ConfigMap у тестовому середовищі**
+
Якщо сценарій вимагає динамічного налаштування мок-сервісу, виконуються наступні кроки:

**   Згенеровані CSV-файли пакуються у POSIX-сумісний архів (`.tar.gz`) за допомогою `Utils.createTarGz()` (використовуючи `apache-commons-compress`).
**   Цей архів копіюється до `infra/deploy-templates`.
**   Jenkins Pipeline, використовуючи `PatchMockService.groovy`, оновлює `ConfigMap` мок-сервісу в цільовому Kubernetes namespace.
**   Виконується rollout/restart deployment'у `sign-mock-service` для застосування нових конфігурацій та даних.

[#pipeline-keycloak-sync]
*   **Синхронізація тестових користувачів із Keycloak**
**   Для забезпечення коректної авторизації, пайплайн запускає службові JMeter-сценарії через Gradle-таски `jmxDeleteKeycloakOfficers` та `jmxCreateKeycloakOfficers`.
**   Ці сценарії видаляють старі та створюють нові облікові записи користувачів у Keycloak на основі згенерованих даних, забезпечуючи узгодженість між мок-сервісом та системою ідентифікації.

[#pipeline-jmeter-run]
*   **Запуск основного JMeter Test Plan**
**   Викликається динамічно згенерована Gradle-таска (наприклад, `runFeatureNestedEntityTestProcess`).
**   Ця таска запускає бінарний файл JMeter (`jmeterExecFile`) у non-GUI режимі, передаючи всі необхідні параметри (шлях до JMX-файлу, кількість потоків, тривалість, шляхи до звітів тощо).
**   JMeter-агенти починають генерацію HTTP-запитів до цільової системи. Метрики в реальному часі відправляються у *InfluxDB* для візуалізації в *Grafana*.

[#pipeline-html-reports]
*   **Генерація HTML-звітів (HTML Reports Dashboard)**
**   Після завершення виконання JMeter автоматично агрегує зібрані дані з `results.csv` та генерує інтерактивний HTML-звіт (*JMeter HTML Dashboard*) у директорії `out/html/`.

[#pipeline-post-actions]
*   **Post-actions (Публікація та архівація результатів)**
+
На фінальному етапі Jenkins Pipeline виконує блок `post { always { ... } }`:

**   **Публікація HTML-звіту:** Директорія `out/html/` публікується за допомогою Jenkins HTML Publisher Plugin, надаючи пряме посилання на звіт в інтерфейсі Jenkins.
**   **Архівація технічних артефактів:** Файли `errors.xml` та `results.csv` архівуються як артефакти збірки, що дозволяє завантажити сирі дані для подальшого аналізу.
