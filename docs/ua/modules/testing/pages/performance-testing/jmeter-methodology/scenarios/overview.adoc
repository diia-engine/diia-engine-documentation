Цей документ надає загальний огляд архітектури проєкту навантажувального тестування. Мета проєкту — забезпечити масштабований, автоматизований та гнучкий процес тестування продуктивності компонентів системи за допомогою Apache JMeter, Gradle та Jenkins.

[#high-level-project-structure]
== Високорівнева структура проєкту

Проєкт має модульну структуру, де кожен компонент (інфраструктура, пайплайни, скрипти навантаження та генератори даних) винесений у відповідну директорію.

[source,text]
----
.
├── ci/                   # Jenkins пайплайни, Job DSL скрипти (seedjob) та параметри запуску
├── gradle/               # Конфігурації Gradle, включаючи спільні таски (common.gradle)
├── infra/                # Інфраструктура (Docker Compose, Grafana, InfluxDB, Jenkins, Traefik)
├── jmeter/               # Файли сценаріїв JMeter (.jmx) та статичні тестові дані
├── src/main/groovy/      # Groovy-класи для генерації тестових даних (Datafaker)
├── build.gradle          # Основний файл конфігурації збірки
└── gradle.properties     # Глобальні змінні та властивості проєкту
----

[#dynamic-job-generation]
=== Динамічна генерація джоб (seedjob.groovy)

Скрипт `*seedjob.groovy*` (Job DSL) виконує роль ініціалізатора (seed job). Після checkout репозиторію скрипт сканує директорію pipelines/, зчитує конфігурації та динамічно генерує Jenkins Jobs за шаблоном `perf-test-<назва-сценарію>`.

[NOTE]
====
Використання `seedjob.groovy` усуває необхідність ручного створення джоб через інтерфейс Jenkins. Усі зміни у пайплайнах або додавання нових тестів застосовуються автоматично після запуску Seed-джоби `*seed-job-pipeline-generator*`.
====

Пайплайни тестування ініціалізуються та підтримуються в актуальному стані за допомогою базової джоби `seed-job-pipeline-generator`, яка розгортається автоматично при старті Jenkins-контейнера (через JCasC).

**Механізми роботи та синхронізації:**

* `*Тригери (SCM Polling)*`
Seed-джоба налаштована на автоматичне опитування репозиторію кожні 15 хвилин (cron-вираз `H/15 * * * *`).
+
[NOTE]
====
Джоба не виконується за розкладом безумовно. Jenkins здійснює лише перевірку стану віддаленого репозиторію. Фактичний запуск генерації пайплайнів (виклик `ci/seedjob.groovy`) відбувається виключно у разі виявлення нових коммітів у цільовій гілці `main`.
====

* `*Життєвий цикл згенерованих джоб (Orphaned Items)*`
Керування тестовими джобами підпорядковується принципу Single Source of Truth (Git). Завдяки директиві `removedJobAction('DELETE')`, Jenkins автоматично відслідковує видалені ресурси.
+
[TIP]
====
Якщо директорію застарілого тестового сценарію видалити з Git-репозиторію, після найближчого SCM-опитування Seed-джоба зафіксує відсутність цільових файлів та самостійно видалить відповідну Job з сервера Jenkins. Ручне очищення не вимагається.
====

[#patch-mock-service]
=== Динамічне налаштування оточення (PatchMockService.groovy)

Утилітарний клас для взаємодії з Kubernetes API з Jenkins Pipeline. Використовується пайплайнами для динамічного оновлення конфігурацій (наприклад, ConfigMap) мок-сервісу перед початком генерації навантаження.

[#groovy-utils]
=== Службові файли розширення Groovy DSL

**`idea.gdsl` та `pipeline.gdsl`** Використовуються IDE (наприклад, IntelliJ IDEA) для забезпечення статичного аналізу коду, автодоповнення (autocomplete) та валідації синтаксису Jenkins Pipeline.

[TIP]
====
Ці файли ігноруються агентами Jenkins під час виконання збірки. Вони призначені виключно для покращення Developer Experience (DX) при написанні пайплайнів.
====

[#ci-pipelines-dir]
=== Життєвий цикл типового тесту (директорія `ci/pipelines/`)

Директорія містить піддиректорії тестових сценаріїв. Кожен сценарій ізольований і має власну конфігурацію, яка складається з двох обов'язкових файлів:

** `*params.json*` — конфігурація параметрів, що описує вхідні параметри для пайплайну. `seedjob.groovy` парсить цей файл для створення параметризованого інтерфейсу (UI `Build with Parameters`). Стандартні параметри включають:
*** `KUBE_URL` — URL API-сервера Kubernetes/Openshift кластера.
*** `NAMESPACE` — цільове середовище (Kubernetes namespace) для ін'єкції навантаження.
*** `MOCK_SERVICE_ROUTE_URL` — Route URL для mock-service.
*** `THREADS` — Кількість користувачів для генерації.

** `*pipeline.groovy*` — Jenkinsfile, що визначає життєвий цикл виконання тесту (checkout коду, підготовка оточення, генерація тестових даних, виклик Gradle-тасок, агрегація логів та публікація звітів).

[#jmeter-dir]
== Сценарії навантаження (JMeter)

Директорія `*jmeter/*` є базовим сховищем артефактів інструменту навантажувального тестування Apache JMeter. Вона містить конфігурації профілів навантаження (test plans) та статичні набори даних від CI/CD пайплайнів та інфраструктурного коду.

[source,text]
----
jmeter/
├── jmx/
│   ├── create-keycloak-users.jmx
│   ├── delete-keycloak-users.jmx
│   ├── feature-multiple-file-saving.jmx
│   ├── feature-nested-entity-test-process.jmx
│   ├── feature-test-read-all-grid.jmx
│   ├── feature-unregistered-role.jmx
│   ├── feature-zvit-pdf-bp.jmx
│   └── reference-iban-update-process.jmx
└── test-data/
    ├── feature-multiple-file-saving/
    │   ├── file-sample_150kB.pdf
    │   ├── ivy_league_cover_letter_template_1_439b5cab58.png
    │   └── sample.pdf
    └── feature-nested-entity-test-process/
        └── doc.pdf
----

[#jmeter-jmx-dir]
=== Бізнес-сценарії та службові скрипти `jmeter/jmx/`

Ця піддиректорія містить файли конфігурації сценаріїв JMeter у форматі XML (`.jmx`). Архітектурно ці скрипти поділяються на дві категорії:

* `*Службові сценарії (Pre-/Post-conditions)*`
До цієї категорії належать скрипти `create-keycloak-users.jmx` та `delete-keycloak-users.jmx`. Їхня мета — підготовка або очищення стану системи до або після основного тесту. Наприклад, масове створення тестових користувачів у Keycloak (ініціалізація сесій) або їхнє подальше очищення для уникнення деградації бази даних між запусками.
+
[NOTE]
====
Службові сценарії викликаються окремими кроками в Jenkins пайплайнах ще до початку основного тесту. Вони не генерують метрик для фінального звіту про продуктивність.
====

* `*Сценарії бізнес-процесів (Main Tests)*`
Файли з префіксами `feature-` або `reference-` (наприклад, `feature-zvit-pdf-bp.jmx`). Це основні тестові плани, які містять конфігурації `Thread Groups` (моделі навантаження), HTTP-семплери, таймери, екстрактори даних та Assertions. Кожен файл відповідає за імітацію навантаження на конкретний ізольований бізнес-процес.

[#jmeter-test-data-dir]
=== Керування статичними даними `jmeter/test-data/`

Призначена для зберігання виключно **статичних** тестових артефактів (payloads), необхідних для виконання сценаріїв із файловими операціями (наприклад, HTTP POST із `multipart/form-data`).

* Структура директорії відповідає назвам сценаріїв (наприклад, директорія `feature-multiple-file-saving` містить файли лише для однойменного JMX-скрипта).
* Містить еталонні файли різних форматів (`.pdf`, `.png`, тощо) і розмірів, які імітують типові сценарії завантаження документів користувачами.

[WARNING]
====
**Вимога до параметризації шляхів:** У JMX-скриптах заборонено використовувати жорстко зашиті (hardcoded) абсолютні шляхи до файлів із цієї директорії. Замість цього необхідно використовувати змінні JMeter (наприклад, `${testDataDir}/feature-multiple-file-saving/sample.pdf`). Значення змінної `${testDataDir}` динамічно прокидається в JMeter агент через аргументи командного рядка під час виклику Gradle-таски.
====

[#src-dir]
== Генерація тестових даних (Data Provisioning)

Директорія `*src/*` містить вихідний код мовою Groovy, який відповідає за динамічну генерацію тестових даних перед початком навантаження. Замість використання статичних датасетів, проєкт генерує унікальні дані (ПІБ, РНОКПП, ЄДРПОУ, дати народження) для кожного запуску.

[source,text]
----
src/
└── main
    ├── groovy
    │   ├── generators
    │   │   ├── AbstractDataGenerator.groovy
    │   │   ├── data
    │   │   │   └── NestedEntityDataGenerator.groovy
    │   │   └── users
    │   │       ├── MockUsersCitizenGenerator.groovy
    │   │       └── MockUsersOfficerGenerator.groovy
    │   └── utils
    │       ├── Person.groovy
    │       └── Utils.groovy
    └── resources
----

[#src-generators-dir]
=== Архітектура генераторів (`generators/`)

Модуль побудовано за патерном Template Method, де загальний алгоритм запису винесено в абстрактний клас, а специфіка генерації рядків — у конкретні імплементації. Це дозволяє повторно використовувати спільну логіку запису CSV та централізовано контролювати формат вихідних даних. Керування кількістю згенерованих записів відбувається через системну властивість `perf.recordsCount` (за замовчуванням 10 записів).

* `*AbstractDataGenerator.groovy*`
Базовий клас, що визначає контракт для всіх генераторів (`getFileName`, `getCsvHeader`, `generateRow`, `postGenerateTask`). Він інкапсулює логіку створення директорій (`testDataDir`) та потокового запису згенерованих даних у файл формату CSV з кодуванням UTF-8.

* `*Піддиректорія users/*` (Генерація користувачів)
Містить класи для створення масивів ідентифікаційних даних:
** `MockUsersCitizenGenerator` — генерує профілі громадян із випадково призначеними типами суб'єктів (`ENTREPRENEUR`, `LEGAL`, `INDIVIDUAL`), ЄДРПОУ (8 цифр) та РНОКПП/ДРФО (10 цифр). Залежно від типу формується роль, наприклад `unregistered-legal`.
** `MockUsersOfficerGenerator` — генерує профілі посадових осіб (чиновників).
+
[NOTE]
====
**Пост-обробка (Post Generate Task):** Обидва генератори користувачів перевизначають метод `postGenerateTask()`. Після створення CSV-файлу вони автоматично викликають утиліту пакування (`Utils.createTarGz`), яка стискає згенеровані дані у файл `.tar.gz` (наприклад, `mock-users.tar.gz`) та переміщує його до директорії `deployTemplatesDir` для подальшого деплою мок-сервісів або завантаження в Keycloak.
====

* `*Піддиректорія data/*` (Генерація бізнес-сутностей)
** `NestedEntityDataGenerator` — відповідає за формування плану виконання (`execution-plan.csv`) для тестування складних сутностей. Генерує специфічні атрибути транзакцій: тип наказу (`ENROLLMENT`, `TRANSFER`, `DISMISSAL`), випадковий номер наказу та поточну дату виконання транзакції.

[#src-utils-dir]
=== Утиліти та Data Transfer Objects (`utils/`)

Директорія містить допоміжні класи, які обслуговують роботу генераторів.

* `*Person.groovy*`
Data Transfer Object (DTO), що описує базову структуру особи в пам'яті (`firstName`, `lastName`, `secondName`, `birthday`). Використовується для типізованої передачі згенерованих даних між методами.

* `*Utils.groovy*`
Допоміжний utility-клас, який реалізує дві основні функції:
. **Генерація реалістичних даних:** Використовує бібліотеку `Faker` з українською локалізацією (`uk_UA`) для вибору реалістичних українських прізвищ, імен та по батькові (з масивів `femalePatronymics`, `malePatronymics` тощо) та випадкових дат народження. Повертає сформований об'єкт `Person`.
. **Робота з файловою системою (I/O):** Реалізує метод `createTarGz`, який за допомогою бібліотеки `commons-compress` (`TarArchiveOutputStream`, `GzipCompressorOutputStream`) створює POSIX-сумісні архіви для Jenkins-пайплайнів.

[WARNING]
====
Оскільки класи генераторів використовують сторонні бібліотеки `net.datafaker:datafaker` та `org.apache.commons:commons-compress`, вони викликаються **до** старту агента JMeter. Переконайтеся, що ці залежності додані до блоку `buildscript { dependencies { classpath ... } }` у конфігурації Gradle, інакше виникне `ClassNotFoundException`.
====

[#gradle]
== Оркестрація збірки (Gradle)

Gradle виконує роль єдиної точки входу (Entry Point) для всіх етапів навантажувального тестування: від підготовки даних до запуску самих JMX-сценаріїв та очищення результатів. Архітектура оркестрації побудована на принципі DRY (Don't Repeat Yourself) та динамічній генерації завдань (tasks).

[#gradle-properties]
=== Глобальні змінні та кордони проєкту

Проєкт не використовує multi-module структуру Gradle і складається з одного кореневого модуля, що підтверджується файлом `settings.gradle`, де визначено: `rootProject.name = 'perf-testing-methodology'`.

Усі константи, шляхи до директорій та імена файлів винесені у файл `gradle.properties`. Це дозволяє керувати інфраструктурними залежностями без втручання в логіку коду:

[source,properties]
----
# Абсолютний шлях до виконуваного файлу JMeter на агенті
jmeterExecFile=/home/jmeter_agent/apache-jmeter-5.6.3/bin/jmeter

# Відносні шляхи до артефактів проєкту
testDataDir=jmeter/test-data
deployTemplatesDir=infra/deploy-templates
jmxFilePath=jmeter/jmx

# Імена генерованих файлів
mockUsersTarGzFileName=mock-users.tar.gz
mockUsersCsvFileName=mock-users.csv
----

[TIP]
====
**Чому це важливо:** Будь-який скрипт пайплайну або Groovy-генератор може отримати ці шляхи динамічно (наприклад, через `Utils.getProperty()`), уникаючи хардкоду.
====

[#gradle-build]
=== Конфігурація збірки (`build.gradle`)

Головний файл `build.gradle` виконує дві критичні функції: підключення залежностей та ініціалізацію тестів.

- **Керування залежностями (Dependencies):**
Блок залежностей містить бібліотеки `datafaker` та `commons-compress`, які необхідні для роботи генераторів. Окремо підключені залежності конфігурації `jenkinsScriptsImplementation` (Jenkins Core, Job DSL), які потрібні для локальної валідації файлу `trigger_seed.groovy`.
Ключовим механізмом є передача Gradle-властивостей у JavaExec-процеси:
+
[source,groovy]
----
tasks.withType(JavaExec).configureEach {
    systemProperties project.properties
}
----
+
Цей блок гарантує, що всі змінні з `gradle.properties` (а також передані через ключ `-P`) будуть доступні всередині Groovy-скриптів під час генерації тестових даних.

- **Динамічна ініціалізація сценаріїв:**
Замість ручного створення `Exec`-тасок для кожного JMX-файлу, використовується масив конфігурацій (map). Скрипт ітерується по списку тестів (наприклад, `feature-unregistered-role`, `feature-test-read-all-grid`) і для кожного викликає замикання `registerJmeterTask`. Якщо тест потребує унікальних параметрів (наприклад, `-JRECORDS_COUNT`), вони додаються через блок `extraArgs`.

[#gradle-common]
=== Спільні конфігурації та принцип DRY (`common.gradle`)

Вся повторювана логіка виконання JMeter винесена в окремий файл `gradle/scenarios/common.gradle`, який імпортується в головний білд-скрипт через `apply from: "gradle/scenarios/common.gradle"`.

Тут зосереджено два типи завдань:

- **Службові таски (Service Tasks):**
* `jmxCleanup` (тип `Delete`): Зчитує змінну середовища `SCENARIO_NAME` і видаляє старі звіти та логи (`out/` та `out/html`) конкретного сценарію перед новим запуском.
* `jmxDeleteKeycloakOfficers` / `jmxCreateKeycloakOfficers`: Виконують допоміжні `.jmx` скрипти для керування тестовими користувачами.
* Таски типу `JavaExec` (наприклад, `groovyGenerateOfficerMockUsers`): Запускають Groovy-класи генераторів, вказуючи `mainClass`.

- **2. Замикання `registerJmeterTask` (Ядро оркестрації):**
Це замикання приймає назву таски, ім'я сценарію та додаткові аргументи, після чого реєструє повноцінне завдання типу `Exec` для виклику процесу JMeter.
+
Воно автоматично:

* Створює необхідні директорії (`doFirst { mkdir ... }`).
* Формує масив аргументів (`baseArgs`) для CLI-виклику JMeter у non-GUI режимі (`-n`).
* Передає параметри профілю навантаження (`-JTHREADS`, `-JRAMP_UP`) з Gradle-властивостей.
* Прив'язує шляхи до звітів (`-l results.csv`, `-e -o htmlDir`) та передає `BUILD_ID` з Jenkins для унікальної ідентифікації запуску.
+
[source,groovy]
----
// Фрагмент формування CLI-команди JMeter з common.gradle
def baseArgs = [
        '-n', '-t', project.file("$jmxFilePath/${scenarioName}.jmx").absolutePath,
        '-l', new File(outputDir, "results.csv").absolutePath,
        '-e', '-o', htmlDir.absolutePath,
        "-JTEST_DATA_DIR=${testDataDir}",
        "-JTHREADS=${project.findProperty('THREADS') ?: '1'}",
        "-JRAMP_UP=${project.findProperty('RAMP_UP') ?: '1'}",
        "-JERROR_LOG_PATH=${new File(outputDir, 'errors.xml').absolutePath}",
        "-JBUILD_ID=${System.getenv('BUILD_NUMBER') ?: 'local'}"
]
----
+
[NOTE]
====
Параметри типу `THREADS` та `RAMP_UP` зчитуються через `project.findProperty()`, що означає, що вони передаються в Gradle через прапорець `-P` (наприклад, `./gradlew runFeature... -PTHREADS=100 -PRAMP_UP=10`). Натомість `BUILD_NUMBER` зчитується через `System.getenv()`, оскільки це нативна змінна середовища, яку інжектує Jenkins під час запуску Pipeline.
====

[#lifecycle-overview]
== Загальна картина: Життєвий цикл та етапи виконання пайплайну

Цей розділ описує наскрізний процес автоматизації — від моменту декларативного створення тестових завдань у Jenkins до збору метрик та очищення середовища після завершення тесту. Завдяки повній інтеграції інструментів (Jenkins Job DSL + Gradle + JMeter CLI), весь процес є повністю автоматизованим і не потребує ручного втручання.

[#pipeline-flow-steps]
=== Покроковий алгоритм роботи системи

Процес виконання навантажувального тестування поділяється на такі послідовні етапи:

. **Ініціалізація та генерація джоб (Jenkins Seed Job)**
+
Оркестрація починається на рівні автоматичного менеджменту інфраструктури Jenkins. Спеціальна задача (`Seed Job`), використовуючи плагін *Jenkins Job DSL* та Groovy-скрипт `ci/seedjob.groovy`, сканує директорію (`pipelines/*`) на наявність файлів `pipeline.groovy` та/або `params.json`. На основі цих даних вона динамічно створює або оновлює індивідуальні Jenkins Pipeline завдання для кожного бізнес-процесу (наприклад, `perf-test-feature-nested-entity`, `perf-test-feature-unregistered-role`).

. **Запуск пайплайну користувачем**
+
Користувач (тестувальник або пайплайн CI/CD) відкриває динамічно створене завдання у Jenkins UI та запускає його через інтерфейс *Build with Parameters*. На цьому етапі задаються ключові параметри для тесту, які передаються як змінні середовища.

. **Отримання вихідного коду (Checkout)**
+
Jenkins-agent виділяє ізольований робочий простір (*Workspace*) та виконує команду `git checkout` для завантаження актуальної версії репозиторію з кодом конфігурацій, скриптів та JMeter-сценаріїв, використовуючи адресу `gitRepoUrl` із глобальних властивостей `gradle.properties`.

. **Локальне очищення**
+
Викликається Gradle-таска `jmxCleanup`, яка повністю видаляє тимчасові директорії та згенеровані масиви даних, залишаючи робочий простір (Workspace) агента чистим перед запуском.

. **Генерація тестових даних через Gradle та Groovy**
+
Пайплайн викликає відповідні Gradle-таски (наприклад, `groovyGenerateOfficerMockUsers`, `groovyGenerateExecutionPlan`), які запускають Groovy-класи генераторів (`MockUsersOfficerGenerator`, `NestedEntityDataGenerator`).
+
Використовуючи бібліотеку `net.datafaker:datafaker`, генератори створюють реалістичні українські персональні дані (ПІБ, дата народження, ЄДРПОУ, ДРФО) та формують плоскі CSV-файли (наприклад, `mock-users.csv` або `nested-entity-execution-plan.csv`) у робочій директорії `jmeter/test-data/`.

. **Patch ConfigMap у тестовому середовищі**
+
Для забезпечення авторизації тестових користувачів та підтримки операцій підпису форм виконується етап підготовки мок-сервісу:

* На рівні Gradle/Groovy-генераторів викликається метод `Utils.createTarGz()`, який за допомогою бібліотеки `apache-commons-compress` пакує згенеровані CSV-файли у POSIX-сумісний архів `mock-users.tar.gz`.
* Сформований архів копіюється до директорії `infra/deploy-templates`, після чого Jenkins Pipeline за допомогою утилітарного скрипта `PatchMockService.groovy` оновлює `ConfigMap` мок-сервісу в цільовому Kubernetes namespace.
* Після оновлення `ConfigMap` виконується rollout/restart deployment'у `sign-mock-service`, що забезпечує підхоплення нових тестових даних без ручного втручання.

. **Синхронізація тестових користувачів із Keycloak**
+
Після оновлення `ConfigMap` та перезапуску `sign-mock-service` пайплайн виконує синхронізацію тестових користувачів у Keycloak.
+
Для цього Gradle послідовно запускає службові JMeter-сценарії `jmxDeleteKeycloakOfficers` та `jmxCreateKeycloakOfficers` у non-GUI режимі.
+
Сценарії виконують такі дії:
+
* Видаляють раніше створені тестові облікові записи з Keycloak для уникнення конфліктів стану між запусками.
* Зчитують актуальний набір користувачів із даних, підготовлених у `mock-users.tar.gz`, та створюють у Keycloak ідентичні облікові записи з відповідними ролями.
+
У результаті мок-сервіс та Keycloak використовують узгоджений набір тестових користувачів, що забезпечує коректну авторизацію та виконання операцій підпису під час основного навантажувального тесту.

. **Запуск основного JMeter Test Plan**
+
Серце пайплайну — запуск головного сценарію навантаження. Gradle динамічно реєструє таску для конкретного сценарію за допомогою замикання `registerJmeterTask`. Викликається бінарний файл `jmeterExecFile` у non-GUI (`-n`) режимі.
+
Під час цього етапу JMeter-агенти (які за потреби масштабуються на кілька ізольованих контейнерів згідно з методологією) починають генерацію HTTP-запитів до цільової системи. Метрики реального часу паралельно відправляються через Backend Listener у базу даних *InfluxDB* для відображення на дашбордах *Grafana*.

. **Генерація HTML-звітів (HTML Reports Dashboard)**
+
По завершенню ітерацій тесту, JMeter автоматично агрегує накопичені у `results.csv` сирі дані транзакцій, помилок та часу відповіді (Latency, Response Time, Percentiles) і компілює їх у статичний інтерактивний веб-звіт (*JMeter HTML Dashboard*) у папку `out/html/`.

. **Post-actions**
+
На фінальній стадії Jenkins Pipeline виконує блок `post { always { ... } }`, який відповідає за публікацію та збереження результатів тестування незалежно від статусу виконання сценарію.
+
* **Публікація HTML-звіту:** Директорія `out/html/`, згенерована JMeter, публікується через Jenkins HTML Publisher Plugin. У результаті в інтерфейсі поточної Jenkins-збірки з’являється окреме посилання в боковій панелі для перегляду HTML-звіту з метриками навантажувального тестування.
+
* **Архівація технічних артефактів:** Файли `errors.xml` та `results.csv` архівуються як build artifacts та прикріплюються до поточної Jenkins-збірки. Це дозволяє завантажити сирі результати виконання та виконати додатковий аналіз або пост-обробку поза Jenkins.

[NOTE]
====
Така схема забезпечує ізоляцію запусків: тестові дані створюються безпосередньо під поточні параметри тесту.
====
